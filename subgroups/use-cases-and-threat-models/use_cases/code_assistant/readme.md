# Code Assistant

Threat-model use case for an AI code assistant (IDE plugin, local and remote agents, model, RAG, MCP servers).

## Complete CycloneDX 2.0 BOM

**[`code_assistant_bom_2.0.json`](./code_assistant_bom_2.0.json)** is the complete CycloneDX 2.0 BOM for this use case. It contains every object, element and value from all of the fragments in [`definition.md`](./definition.md): all 23 components (declared in `definitions.components` and associated with the Code Assistant system by reference through `inventories`), 3 actors (with their parties), 3 zones, 3 boundaries (without zone-crossing requirements, which are not considered at this time), 23 flows, the structural relationships, and the 3 use cases. The optional blueprint `assets` example in `definition.md` is intentionally not included. It validates against the CycloneDX 2.0 bundled JSON schema ([`cyclonedx-2.0-bundled.schema.json`](../../../../.bob/skills/cyclonedx/schema/2.0/cyclonedx-2.0-bundled.schema.json)). Use this file for tooling and analysis of the model in `definition.md`. The threat-model BOMs are sliced from a different, generated system BOM; see [Which system BOM to use](#which-system-bom-to-use).

### Which system BOM to use

There are two system BOMs for this use case, and they are not kept in step:

- [`code_assistant_bom_2.0.json`](./code_assistant_bom_2.0.json) is maintained by hand with `definition.md`, and is the source of truth for that document.
- [`code_assistant_system_bom.generated.json`](./code_assistant_system_bom.generated.json) is generated from the diagram, and is the one the threat-model BOMs are sliced from. It differs where the 2026-05-12 diagram differs from the notes, and it records each difference as an assumption.

A change to `code_assistant_bom_2.0.json` does not reach the threat-model BOMs. To change the threat model, update the generated system BOM (and bump its `version`), then re-slice each threat-model BOM with `slice_use_case.py --update`, as [the threat-model workflow](../../../../.bob/skills/cyclonedx/workflows/system-bom-to-threat-model.md#regenerating-after-the-system-bom-changes) describes.

The element descriptions in the generated system BOM say what each element is and does, with no threat language, following the convention proposed in issue #64. That issue is still open; it adds the rule to the diagram-to-system-bom workflow, so until it merges a regenerated BOM may bring threat wording back.

The threat-model BOMs were produced with the working group's threat spreadsheet ([`threats/`](./threats/)) in view, to close the gaps a comparison found. They are a baseline for future runs of the skill, not a blind test of it.

## How the documents relate (what was simplified)

[`definition.md`](./definition.md) explains the model piece by piece. Its JSON snippets are **fragments**, each showing one part of the BOM (for example only the `actors`, or only the flows for one sub use case). Its closing section, "CycloneDX v2.0 — Code Assistant Threat Model BOM", assembles the pieces into one document but is a **simplified view**: it keeps the structure and mostly the required fields (`refId`, `name`, `type`, `source`, `destination`, and so on) so the overall shape is easy to read, and it leaves out descriptions, permissions, preconditions, postconditions, exceptions, success criteria, notes and other optional detail.

If `definition.md` and `code_assistant_bom_2.0.json` ever differ, [`code_assistant_bom_2.0.json`](./code_assistant_bom_2.0.json) is authoritative.
